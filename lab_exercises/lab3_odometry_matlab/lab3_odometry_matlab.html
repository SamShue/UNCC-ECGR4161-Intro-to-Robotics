Lab 3: MATLAB Odometry

In this lab, you will implement odometry in MATLAB using ROS Toolbox. The Raspberry Pi will run only the astar_bridge node, which publishes encoder ticks. Your MATLAB script will subscribe to /encoder_ticks, estimate robot pose, and publish the resulting odometry to RViz.

This lab keeps the control and estimation workflow inside MATLAB instead of modifying the romi_base Python node.

Required Materials

  • Romi32U4 robot with Raspberry Pi 4B
  • Raspberry Pi image prepared from Lab 1
  • MATLAB with ROS Toolbox
  • WSL2 with ROS 2 Humble installed
  • Windows laptop
  • 6x AA batteries

Background

What is Odometry?

Odometry estimates a robot’s position (x, y) and heading (θ) from motion sensors. For the Romi, the wheel encoders tell us how far each wheel traveled, and we use differential-drive kinematics to integrate that motion into a pose estimate.

Note: Odometry drifts over time. Wheel slip, uneven floors, and small calibration errors will accumulate, so the goal is a reasonable estimated path, not perfect truth.

Forward Kinematics

To update pose from encoder motion, convert wheel travel into center displacement and heading change:

Δs = (dL + dR) / 2
Δθ = (dR - dL) / L

xnew = xold + Δs · cos(θold)
ynew = yold + Δs · sin(θold)
θnew = θold + Δθ

Bridge-Only Workflow

  • The Pi runs astar_bridge.
  • Your MATLAB script publishes /odom using the encoder stream.
  • For visualization, RViz subscribes to /odom and shows the estimated path in the odom frame.

3. Odometry Starter Script

Use the script below as your starting point. It subscribes to encoder ticks, computes pose updates, and publishes a ROS 2 odometry message.

% romi_lab3_odometry.m
% MATLAB odometry for ROMI Lab 3

clear;
clc;

setenv('ROS_DOMAIN_ID', '0');

node = ros2node('/romi_lab3_odometry');
encSub = ros2subscriber(node, '/encoder_ticks', 'std_msgs/Int32MultiArray');
odomPub = ros2publisher(node, '/odom', 'nav_msgs/Odometry');

odomMsg = ros2message(odomPub);

% Robot parameters
wheelBaseM = 0.141;
wheelDiameterM = 0.07;
ticksPerRev = 1440.0;
wheelCircumferenceM = pi * wheelDiameterM;

% Pose state
x = 0.0;
y = 0.0;
theta = 0.0;

% Encoder history
prevTicks = [];
prevTime = tic;

fprintf('Starting ROMI odometry loop...\n');

while true
    if encSub.NumMessagesAvailable == 0
        pause(0.01);
        continue;
    end

    encMsg = receive(encSub, 1.0);
    currentTicks = double(encMsg.data(:));

    if numel(currentTicks) < 2
        warning('Expected encoder data in [left, right] format.');
        continue;
    end

    dt = toc(prevTime);
    prevTime = tic;
    if dt <= 0
        dt = 1e-3;
    end

    if isempty(prevTicks)
        prevTicks = currentTicks;
        continue;
    end

    deltaTicks = currentTicks - prevTicks;
    prevTicks = currentTicks;

    leftDistanceM = (deltaTicks(1) / ticksPerRev) * wheelCircumferenceM;
    rightDistanceM = (deltaTicks(2) / ticksPerRev) * wheelCircumferenceM;

    deltaS = (leftDistanceM + rightDistanceM) / 2.0;
    deltaTheta = (rightDistanceM - leftDistanceM) / wheelBaseM;

    thetaMid = theta + deltaTheta / 2.0;
    x = x + deltaS * cos(thetaMid);
    y = y + deltaS * sin(thetaMid);
    theta = theta + deltaTheta;

    if dt <= 0
        dt = 1e-3;
    end

    linearVelocity = deltaS / dt;
    angularVelocity = deltaTheta / dt;

    qz = sin(theta / 2.0);
    qw = cos(theta / 2.0);

    odomMsg.header.stamp = ros2time(node);
    odomMsg.header.frame_id = 'odom';
    odomMsg.child_frame_id = 'base_link';
    odomMsg.pose.pose.position.x = x;
    odomMsg.pose.pose.position.y = y;
    odomMsg.pose.pose.position.z = 0.0;
    odomMsg.pose.pose.orientation.x = 0.0;
    odomMsg.pose.pose.orientation.y = 0.0;
    odomMsg.pose.pose.orientation.z = qz;
    odomMsg.pose.pose.orientation.w = qw;
    odomMsg.twist.twist.linear.x = linearVelocity;
    odomMsg.twist.twist.angular.z = angularVelocity;

    send(odomPub, odomMsg);

    fprintf('x=%.3f  y=%.3f  theta=%.3f  v=%.3f  w=%.3f\n', x, y, theta, linearVelocity, angularVelocity);
end

4. Run the Motion Test

Use the Lab 2 MATLAB motion or controller workflow to drive the robot in a square while this odometry script runs. The key requirement is that the robot motion produces encoder data that your MATLAB odometry loop can integrate into a square-shaped path.

If you need a simple status indicator, you may publish LED values from MATLAB while the test runs.

5. Launch RViz

Open a local WSL terminal and launch RViz:

rviz2

Side Note — RViz won’t render? In WSL, RViz sometimes opens as a black or blank window, fails to draw, or crashes on startup because of OpenGL/GPU limitations. If that happens, force RViz to use software rendering:

export LIBGL_ALWAYS_SOFTWARE=1
rviz2

Configure RViz as follows:

  • Set the Fixed Frame to odom.
  • Add the /odom display.
  • Add a TF display if your MATLAB setup is also broadcasting transforms.

6. Verify the Square Path

Run the same square-motion test used in Lab 2 while the odometry loop is active. RViz should show an estimated path that resembles a square, and the robot should return close to its starting position after the fourth side.

Important: Do not tune the robot motion to hide odometry problems. If the physical path is poor, tune the Lab 2 controller. If the RViz path looks wrong, debug your MATLAB odometry equations and frame handling.
